# GEN-UI · 四种典型任务用法

> 以下是可复制的**任务提示词与期望输出形式**，不是模型生成或通过验收的证据。请根据实际项目替换输入数据。

## 一、普通问答：默认 Markdown

**示例提示词：**“解释 Java 线程池为什么需要有界队列，区分等待积压、拒绝策略和延迟风险；不要生成图表或 HTML。”

**交付形态：** 简短结论 + 原理 + 主要风险。不要套用代码实施任务的“改动文件”“必须验收”模板，不虚构压测结果。

参考已有 [线程池示例](../examples/thread-pool.zh-CN.md)。

## 二、技术方案对比：统一表格

**示例提示词：**“比较 RabbitMQ 和 Kafka 的消息模型、消费方式、顺序、吞吐前提、运维成本与适用场景；按同一组维度对比，不提供未经测量的性能数据。”

**交付形态：** 一张同维度对比表格 + 有条件的选型建议。Kafka 分区内顺序不能扩展为全局顺序，RabbitMQ 的队列和 Streams 不应混为一谈。

## 三、架构技术评审：事实与建议分开

**示例提示词：**“评审 StoryOS 的 STORY → STORYBOARD → PRODUCTION → QUALITY REVIEW → RELEASE；20 张图片中 12 成功、5 运行中、3 失败；MySQL 持久化状态，Redis 用于心跳和辅助调度，Outbox 负责可靠事件。Worker B 接管 A 的过期租约后，如何拒绝 A 的迟到写回？给出风险与待验收项。”

**交付形态：** 阶段关系、12/5/3 进度、Worker 接管和 fencing 风险矩阵、最小验收建议。阶段准入条件未提供，应写待定义而不是“系统一定不允许进入 QUALITY REVIEW”。缺少压测与演练记录时不能宣称通过。

普通评审直接用 Markdown；只有图能清楚表达真实关系时才按需升级。

## 四、静态 HTML 文档：内容优先

**示例提示词：**“把技术评审整理成仓库内可离线阅读的中文 HTML 文档，包含真实左侧章节导航、风险表、验收列表和移动端布局；无需筛选、分页、弹窗、仪表盘。没有证据的事项应标待验证。”

**交付形态：** 按 [静态 HTML 要点](../references/html-report-essentials.md)，引用仓库中真实存在的本地资源；目录锚点指向真实正文，不制造无操作的按钮或虚构资源路径。

**升级条件：** 真正独立单文件、复杂图表/交互、语义图或多页门户，应使用 [完整 HTML 合约](../references/html-report-contract.md)，不可静默删减用户需要的功能。

## 按需补充：多轮设计评审与收口判断

**示例提示词：**“这是 StoryOS 第二轮评审：第一轮提出 Worker 迟到写回风险，本轮已补执行权检查，但故障注入尚未运行。只告诉我本轮改变了什么、哪些要求仍有遗漏、现在是否可以收口；不要重述整套架构。”

**交付形态：** 当前变化 → 有依据的结论 → 仍未解决/未验证事项 → 可收口、有条件收口或暂不收口的**建议**。代码有修改但无测试证据时仍标“待验证”；非致命缺陷不能默认由 AI 代替用户接受。需要追溯时才展示 [最小决策台账](../references/reading-layers.md)，不新增数据库或固定输出模板。

## 通用边界

- “报告”“架构”“设计”本身不是 HTML 触发词；按用户明确的交付物选择。
- 以上数据属于示例输入，不代表真实生产指标、线上结果或代码修改。
- 2026-11-13 本轮没有调用模型和浏览器，也没有运行自动化测试。
