# GEN-UI 下一阶段方向指导

> **产品定位：AI Information Design Skill（AI 信息设计 Skill）**
> **核心主张：UI 是表达手段，信息理解才是目的。**
> Teach AI to Design Information, Not Just Interfaces.

- 文档性质：下一阶段产品方向与设计指导
- 适用范围：GEN-UI Skill、References、Assets、Tests、Evals

## 一、方向结论

> **最高优先级：GEN-UI 永远以 Skill 为唯一产品定位。**
>
> 不盲目扩张产品边界，不为了功能丰富而增加功能，不把 Skill 发展成 UI 框架、组件库、独立工具平台或复杂运行时。
>
> 所有能力建设必须围绕一个目标：教会 AI 更好地理解信息、组织知识、选择表达形式并交付高质量内容。新能力优先通过更好的指导原则、决策规则和按需加载的参考资料解决；只有当 Skill 指导本身无法解决真实问题，且有充分证据证明必要时，才考虑增加实现资源。
>
> **本原则对所有后续功能、路线、技术选型和版本规划拥有最高优先级与否决权。与其冲突的提案不进入 GEN-UI 范围。**

GEN-UI 应继续保持为一个 **Skill**，不转型为 UI 框架，也不以建设独立可视化平台为目标。

它要教会 AI：

1. 理解信息、任务目标和读者；
2. 组织知识，提炼重点与关系；
3. 根据内容选择恰当的表达形式；
4. 使用文字、表格、图表或 HTML 完成表达；
5. 检查交付物是否准确、完整、清晰、易于使用。

**成功标准不是生成了多少 UI，而是读者是否更快、更准确地理解并使用信息。**

### 当前阶段的战略取舍

- 保留 Markdown 默认、HTML 按需、语义图按需的渐进式能力。
- 暂缓新增图表类型和复杂视觉组件。
- 优先建设信息设计决策、信息组织方法和真实 Agent 行为评估。
- 继续以跨 Agent、离线可用、低上下文成本为约束。
- 稳定性整改与本方向并行，但不以新功能掩盖已有缺陷。

## 二、产品定位与边界

### 2.1 使命

让复杂信息更清晰，让重要知识更容易被理解，让有价值的内容更容易被使用。

GEN-UI 不是“让 AI 把回答变漂亮”的装饰工具，而是帮助 AI 形成稳定的信息设计习惯。

### 2.2 它是什么

- 一个指导 AI 进行信息理解、知识组织和表达决策的 Skill。
- 一套按需加载的表达规范与实现资源。
- 一套验证输出质量、规则遵循和能力兼容性的测试体系。

### 2.3 它不是什么

- 不是通用前端框架或 UI 组件库。
- 不是必须将普通回答转换成 HTML 的渲染器。
- 不是图表数量越多越好的可视化集合。
- 不是替代事实核查、代码评审、测试或业务判断的工具。
- 不是绑定 Codex、Claude 或某个模型的专有工作流。

## 三、五项核心能力

| 核心能力 | AI 应该学会什么 | 交付价值 |
| --- | --- | --- |
| 信息理解 | 识别任务目标、读者、上下文、约束和决策点 | 知道读者真正需要理解什么 |
| 知识组织 | 提炼结论、证据、概念、因果、依赖、风险和行动 | 把零散信息组织成有意义的结构 |
| 表达决策 | 判断文字、列表、表格、流程图、语义图或 HTML 是否必要 | 用最小复杂度表达信息 |
| 信息呈现 | 控制层级、重点、布局、可读性和必要交互 | 降低阅读与理解成本 |
| 质量自检 | 检查事实边界、完整性、可访问性、表达适配和回退能力 | 避免“好看但错误”或“完整但难读” |

## 四、端到端工作闭环

1. **理解任务与读者**：读者是谁？需要理解、比较、决策、执行还是验收？
2. **识别信息结构**：区分事实、用户输入、推断、建议、风险和待确认事项。
3. **组织知识**：建立结论、证据、原因、关系、步骤和行动之间的结构。
4. **选择表达形式**：选择足以解决理解问题的最简单形式。
5. **生成内容**：先保证内容准确，再使用合适的视觉和交互手段。
6. **质量自检**：检查是否遗漏关键信息、是否误用图表、是否引入不必要复杂度，以及增强失败时是否仍可阅读。

这是一套思考流程，不是要求每个回答都输出六个固定章节。简单问题可以直接回答；复杂任务才逐步展开。

## 五、表达形式决策原则

| 信息特征 / 阅读任务 | 首选表达 | 使用边界 |
| --- | --- | --- |
| 简单解释、结论、短建议 | Markdown 段落 | 不为视觉效果增加容器 |
| 并列要点、操作步骤 | 列表 | 有顺序才使用有序列表 |
| 多方案、多指标比较 | 表格 | 控制列数，突出真正影响决策的数据 |
| 明确的先后、分支、状态流转 | 流程图 / 活动图 | 只有关系能帮助理解时才画 |
| 多参与者调用与消息顺序 | 时序图 | 参与者、消息和时间顺序必须有依据 |
| 层级、归属、分类 | 思维导图 / 分层结构 | 归属关系不应伪装成调用连线 |
| 系统边界、组件、部署与依赖 | 架构视图 / 拓扑图 | 只连接真实依赖，不为布局制造关系 |
| 长篇、分章节、需要导航的独立文档 | 离线 HTML | 用户明确需要或阅读场景确有价值时才使用 |
| 需要探索的复杂关系 | 可交互语义图 | 交互必须提升理解，不能只是装饰 |

**决策顺序：先判断信息要解决什么理解问题，再选表达形式；不能先决定画图，再勉强寻找内容填充。**

## 六、必须坚持的设计原则

1. **Content First（内容优先）**：事实、逻辑和完整性优先于视觉效果。
2. **Reader First（读者优先）**：围绕读者的理解任务组织内容，不围绕组件组织内容。
3. **Right Representation（恰当表达）**：只使用能降低理解成本的表达形式。
4. **Minimalism（最小复杂度）**：能用 Markdown 讲清楚，就不生成 HTML；能用表格讲清楚，就不强行画图。
5. **Progressive Enhancement（渐进增强）**：Markdown 是可靠基础，HTML 与交互能力按需加载；增强失败不能损坏主要内容。
6. **Information Integrity（信息完整与真实）**：不得为了视觉简化而改变含义、遗漏限制或虚构证据。
7. **Agent Agnostic（跨 Agent）**：优先使用标准 Markdown、HTML、JSON、SVG 和可移植文件约定。
8. **Graceful Fallback（安全回退）**：宿主不支持交互时，仍交付可读文本、静态图或完整 Markdown 解释。
9. **Evidence Before Claims（证据优先）**：示例、推断、计划、实际执行结果必须明确区分。

## 七、Skill 能力分层

| 层级 | 定位 | 加载策略 | 内容边界 |
| --- | --- | --- | --- |
| L1 · Core | 信息设计核心 | 默认加载 | 任务理解、知识组织、表达决策、Markdown 基础和质量原则 |
| L2 · HTML | 长文档呈现 | 明确需要 HTML 时加载 | 页面层级、导航、布局、表格、代码、离线与可访问性规范 |
| L3 · Visualization | 专业关系表达 | 复杂关系确实需要时加载 | 七类语义图、JSON 契约、SVG 引擎、交互与专项测试 |
| QA · Evaluation | 能力保障 | 开发、评审和验收时使用 | 自动化测试、浏览器测试、Agent A/B、案例库 |

### 资源职责

- SKILL.md：入口、意图识别、决策路由和最小验收要求。
- references/：按需读取的详细原则、HTML 契约、图表模型和架构表达规则。
- assets/：经过审查的静态 CSS、JavaScript、SVG 等实现资源。
- tests/：验证功能正确性、边界行为、回归和离线能力。
- evals/：验证不同 Agent 是否正确理解并使用 Skill。
- docs/：产品定位、设计决策、版本方向和开发说明。

不要为了让核心文件看起来完整，把高级实现细节重新复制进 SKILL.md。也不要因为某项资源默认不加载，就删除已经成熟的高级能力。

## 八、下一阶段建设路线

### 阶段 0：完成当前版本稳定性收口

**目标：先让现有能力可靠，不把未解决问题带入下一阶段。**

- 完成当前并行改动的整合评审。
- 修复桌面与移动端目录等已知回归。
- 验证现有七类语义图、架构视图和 HTML 离线行为。
- 保持随机边界测试、浏览器测试和历史回归可重复运行。
- 对未完成的真实 Agent A/B 明确标记，不以静态检查代替行为证据。

### 阶段 1：智能信息设计决策（下一阶段主线）

**目标：让 AI 知道“应该怎样表达”，而不是只知道“有哪些组件”。**

建议建设：

1. 一份轻量的 information-design-decision 参考规则，覆盖读者任务、信息复杂度、表达形式选择和反例。
2. 简单、比较、流程、架构、长文档等典型场景的决策样例。
3. 对“应该用 Markdown 却生成 HTML”“应该用关系图却只堆表格”等误判建立测试用例。
4. 将决策原则接入核心路由，但保持 SKILL.md 轻量。
5. 对不确定场景优先选择简单表达，避免过度设计。

**阶段验收：** 对相同任务，Agent 能解释或稳定表现出合理的表达选择；普通问答不会无故升级成 HTML 或复杂图表。

### 阶段 2：真实 Agent 行为评估

**目标：证明轻量化没有损害能力，且新决策确实提升输出质量。**

至少覆盖三种任务：

- Markdown：日常解释、技术分析、结论与风险组织。
- HTML：用户明确要求独立长文档时，能否按需加载规范并生成离线页面。
- Visualization：业务关系复杂且有依据时，能否选择正确图表并遵守数据契约。

评估维度：

- 表达形式选择是否合理；
- 结论、证据、限制和行动是否完整；
- 是否出现事实编造或含义失真；
- HTML 和图表是否按需加载；
- 输出是否可读、可访问、可离线使用；
- Token 与上下文成本是否合理。

建议采用同模型、同任务、同参考资料的新旧 Skill 对照；保存原始输出、模型版本、运行参数、失败原因和人工评分。额度不足、超时或未运行必须记录为未完成，不计入通过。

### 阶段 3：案例与交互能力增强

**目标：让用户看见信息理解的改善，而不是只看见页面更漂亮。**

- 建立项目分析、架构设计、技术实施、测试验收四类代表性案例。
- 每类案例提供 Before / After 和真实内容差异说明。
- 在现有语义图上探索节点详情、步骤浏览、层级展开和正文联动。
- 只有当交互明显降低理解成本时才保留。
- 不以增加图表类型作为版本目标。

## 九、功能准入评审

任何新功能、规范或资源进入 GEN-UI 前，必须回答：

1. 它解决了哪一种真实的信息理解问题？
2. 现有 Markdown、表格或已有图表为什么不够？
3. 它会不会增加默认上下文、安装、运行或维护成本？
4. 能否按需加载，并在不支持时安全回退？
5. 是否跨 Agent、离线可用，并且不依赖不可信脚本？
6. 是否有独立测试证明收益，并覆盖回归风险？

### 决策规则

- 没有明确理解收益：不做。
- 只是视觉装饰：不做或降级为可选。
- 默认增加复杂度：优先重设计加载路径。
- 只对单一 Agent 有效：先评估是否应放入适配层，而不是核心。
- 无法验证效果：先做实验，不直接进入稳定能力。
- 现有能力已经足够：复用，不重复造组件。

## 十、质量指标与验收方法

以下是建议建立的指标，不代表当前已经达到的成绩。先收集基线，再确定正式阈值。

| 维度 | 观察指标 | 验收方法 |
| --- | --- | --- |
| 决策质量 | 表达形式适配率、过度设计率 | 固定任务集 + 人工评分 |
| 信息质量 | 结论、依据、限制、行动完整度 | 结构化评分与事实核对 |
| 信息完整性 | 虚构事实、丢失约束、语义失真 | 对照输入逐项检查 |
| 轻量化 | 默认加载资源数、上下文 Token、输出长度 | 记录真实 Agent 运行数据 |
| 可用性 | 离线、键盘、移动端、交互成功率 | 浏览器自动化与人工抽检 |
| 兼容性 | 不同 Agent 的规则遵循情况 | 跨 Agent 同题评测 |
| 稳定性 | 边界缺陷、回归失败、重复初始化问题 | 固定种子压力测试与回归套件 |

**禁止只用测试通过率代表产品质量。** 测试集是否覆盖真实任务、失败样本是否有代表性、评估是否独立，同样重要。

## 十一、明确的非目标

下一阶段暂不投入：

- 新增第八、第九种语义图类型；
- 为普通 Markdown 回答增加页面外壳；
- 大量动画、装饰性卡片和无业务意义的交互；
- 独立在线图表编辑器、账户系统或协作平台；
- 绑定某个模型或 Coding Agent 的专有实现；
- 仅为了提高截图观感而改变内容结构；
- 将 HTML、SVG、JavaScript 实现细节重新塞进核心 Skill。

## 十二、下一阶段建议交付清单

建议按以下顺序推进：

- [ ] 当前版本已知回归全部收口，形成可信稳定基线。
- [ ] 梳理并确定信息设计决策模型及反例。
- [ ] 新增按需加载的决策参考文档，不显著增加核心 Skill 体积。
- [ ] 建立 Markdown / HTML / Visualization 三类代表性任务集。
- [ ] 完成新旧 Skill 的真实 Agent A/B，保留原始输出与评分。
- [ ] 根据失败样本迭代规则，而不是凭主观继续增加规则。
- [ ] 更新 Before / After 案例，证明信息理解成本确实下降。
- [ ] 完成跨 Agent 与浏览器回归，再决定下一版本是否封版。

## 十三、最终产品原则

> **GEN-UI 不是教 AI 如何生成漂亮的页面，而是教 AI 如何理解信息、组织知识、选择表达形式，并交付高可读性、高质量的信息成果。**

无论最终交付的是一段 Markdown、一张表格、一幅架构图，还是一份交互式 HTML 文档，都必须服务于同一个目标：

**让复杂的信息变得清晰，让重要的知识更容易被理解，让有价值的内容更容易被使用。**

UI 是手段，信息理解才是目的。
