Before → after

Before: “Thread-pool sizing depends on CPU, I/O, queues, latency and many other settings...” After: Use a bounded queue, define rejection behavior, and measure workload and tail latency before choosing pool sizes.

1. Answer first, then support it

Recommendation

Use a bounded queue and explicit rejection policy. Determine pool size from observed workload rather than a fixed rule.

Why: CPU-bound and blocking I/O tasks have different resource bottlenecks. Next: Measure P95/P99 latency, CPU use, and queue wait.

Open question

Is the workload CPU-bound or mostly waiting on external I/O?

3. Explain processes as steps

  1. Inspect: verify the existing API and task model.
  2. Decide: document state invariants and what will not change.
  3. Implement: introduce the smallest safe change.
  4. Verify: run reproducible checks and record actual outcomes.

5. Make planned work explicit

  • ⏳ Define the task state-machine contract — not started.
  • ⏳ Add fenced writes and Outbox delivery — not started.
  • ❓ Confirm the maximum provider call duration.
  • ⚠️ Do not mark a change complete without commit and test evidence.

9. Navigate long technical documents

Choose the document according to the reader’s task, not a generic UI template.

  1. Project analysis report — understand the system and risks.
  2. Architecture design — understand ownership and recovery.
  3. Implementation plan — execute a safe change.
  4. Test and acceptance — verify outcomes with evidence.

10. Use interaction only when it improves reading

For large datasets, use relevant filters, 10-row pagination, optional column visibility, and accessible overflow tooltips. For a real flow, use offline SVG zoom, pan, and fullscreen. For code, offer one-click copy. These are tools for comprehension, not the product itself.
