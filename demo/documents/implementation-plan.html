ENGINEERING DOCUMENT / SANITIZED CASE

技术实施方案 · 可靠异步任务编排改造

将长耗时工作流从同步执行改造为持久化驱动的异步任务体系，按基线梳理、核心改造、恢复能力和上线验收四个阶段交付。

实施策略

先明确状态模型和消息契约，再落地 Outbox、幂等消费与 Fencing，最后通过故障注入和灰度发布验证恢复能力。任何阶段都以可复现证据作为退出条件。

一、 实施目标与改造范围

本实施方案将同步、单进程内的长任务执行方式，逐步改造为持久化驱动的异步任务编排。目标是保证任务可追踪、可恢复、可幂等处理，并使节点执行结果能够被可靠汇总。

改造范围
范围本次实施明确不做
任务模型Run、Node、Task、Attempt 状态与关联重构无关业务领域模型
任务执行调度、Outbox、Worker 领取与回写替换所有模型供应商
一致性乐观锁、Fencing Token、消费幂等宣称端到端 exactly-once
恢复能力过期任务对账、断点恢复、事件留痕自动修复所有业务数据错误
可观测性统一关联 ID、关键指标和失败分类本期建设完整数据分析平台

二、 实施阶段与依赖关系

推荐按“先明确契约，再打通可靠执行，最后补齐恢复和验收”的顺序推进。任何阶段如果发现当前数据模型无法表达执行权或尝试历史，应先修正模型，不应通过临时缓存字段绕过。

三、 详细实施任务

（一） 阶段一：现状与契约梳理

  1. 盘点任务入口、节点执行器、消息消费者、状态写入和结果存储位置。
  2. 列出所有状态字段及其写入方，识别是否存在多个模块同时修改最终状态。
  3. 确定业务幂等键、Task 唯一性、Attempt 编号规则和外部请求关联 ID。
  4. 输出状态迁移图、失败分类表和兼容策略，组织架构评审。

（二） 阶段二：持久化任务与可靠投递

  1. 新增或调整 Run、NodeExecution、Task、Attempt、Outbox 数据结构及必要索引。
  2. 将任务创建和 Outbox 事件写入同一事务，明确事件版本与载荷契约。
  3. 实现 Outbox Publisher 的批量扫描、发布重试、发布确认和积压监控。
  4. Worker 消费时先做幂等判断，再领取任务，执行结果使用条件更新提交。

（三） 阶段三：执行权与恢复

  1. 领取任务时递增 fencing token，并将 token 绑定到 Attempt。
  2. Worker 心跳只续租当前 token；过期执行者不得继续提交最终结果。
  3. Reconciler 分页扫描超时 RUNNING、未发布 Outbox 和异常聚合节点。
  4. 恢复过程生成独立 Event，记录旧 token、新 token、原因和恢复决策。

（四） 阶段四：验证与上线

  1. 执行状态机、重复投递、并发竞争、进程终止和恢复对账测试。
  2. 在集成环境模拟供应商超时、限流和未知响应结果。
  3. 先对内部测试任务灰度，再扩大任务类型和并发规模。
  4. 观察核心指标达到约定窗口后，完成上线验收与文档归档。

五、 数据迁移与兼容策略

  1. 字段扩展：先增加可空字段、索引和新表，不立即删除旧字段。
  2. 双读校验：在测试环境并行计算旧状态与新状态聚合结果，记录差异，不双写两个最终状态源。
  3. 历史数据回填：按批次生成 Task / Attempt 关联；无法还原的历史执行标记为 LEGACY，不伪造 Attempt 证据。
  4. 切换写入：以功能开关按任务类型或租户切换新执行链路。
  5. 清理旧路径：观察期结束并确认无旧消费者后，再移除旧字段和过渡逻辑。

（一） 回滚步骤

  1. 关闭新任务入口或功能开关，停止产生新的新格式任务。
  2. 保留 Worker 对已领取任务的安全收尾策略；不得直接删除 RUNNING 任务。
  3. 对未完成任务执行对账，确认可继续、可重试或需人工介入。
  4. 恢复旧入口时只处理旧格式兼容数据；新格式任务保留独立恢复通道。
  5. 记录回滚原因、影响范围、任务清单和数据补偿结果。

八、 交付物与验收标准

  • 架构设计与状态迁移说明经评审通过。
  • Task、Attempt、Outbox 数据模型及索引说明齐全。
  • 核心状态写入统一经过条件更新与 fencing 校验。
  • 重复投递、旧 Worker 延迟回写、进程崩溃和恢复对账用例具备可复现证据。
  • 灰度、回滚和人工补偿步骤可由值班人员按文档执行。
