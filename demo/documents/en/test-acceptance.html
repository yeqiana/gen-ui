Test and acceptance plan

Risk-based tests and verifiable acceptance gates for asynchronous task consistency and recovery.

Read this first

The following material is an illustration of evidence-aware technical writing. Its scope, assumptions, decisions, and next actions are explicit; no code audit, test run, or deployment is implied.

1. Test strategy

Do not test only successful execution. Cover illegal transitions, duplicate delivery, concurrent claims, expired leases, crashes, retry classification, authorization, and evidence correlation. Record exact environment, commit, script, and data versions.

2. Isolated environment

Use a test database, a dedicated queue, and a mock model provider. Allow controlled pause, network delay, worker termination, and duplicate message replay. Never run destructive fault injection against production.

3. Core test matrix

Every test case needs its initial state, injected fault, expected database transition, event evidence, and reproducible assertion. Without execution evidence, its state remains Not run.

4. Fencing failure injection

Pause Worker A after claim. Let its lease expire. Worker B claims the task with a higher fencing token and commits a result. Resume A; its stale conditional update must affect zero rows.

5. Performance and recovery

Measure queue wait, throughput, P95/P99, Outbox lag, connection-pool saturation, and recovery convergence at graduated concurrency. Proposed workloads are test inputs—not measured capacity.

6. Release gates

Require zero invalid terminal overwrites, idempotent redelivery, successful crash reconciliation, audit-ready evidence, and an executed rollback drill. No gate is marked passed in this demonstration.
