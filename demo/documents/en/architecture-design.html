System architecture design

A durable task architecture with explicit ownership, idempotent delivery, and restart recovery.

Read this first

The following material is an illustration of evidence-aware technical writing. Its scope, assumptions, decisions, and next actions are explicit; no code audit, test run, or deployment is implied.

1. Goals and invariants

Every state transition is versioned; only the current execution owner can commit results; duplicate messages cannot create duplicate business effects; and recovery actions leave traceable evidence.

2. Component responsibilities

The API handles authorization and run creation. The orchestrator evaluates dependencies. The scheduler dispatches tasks. Workers run attempts through provider adapters. MySQL stores authoritative state; Redis provides heartbeat hints; the broker offers at-least-once delivery.

3. Task state machine

A task transitions from PENDING to RUNNING, then SUCCEEDED, FAILED, BLOCKED, or CANCELLED. A retry requires an explicit policy decision and a new Attempt. Provider-call success and content-quality acceptance remain separate.

4. Fencing and conditional writes

When a worker claims a task, the database increments its fencing token. The final commit includes the token so that a stale worker cannot overwrite a newer owner's result.

Example conditional update:

UPDATE task
SET status = 'SUCCEEDED', version = version + 1
WHERE task_id = :task_id
  AND status = 'RUNNING'
  AND fencing_token = :current_token;

5. Delivery and recovery

Commit the task transition and Outbox event together. Publish asynchronously and accept possible redelivery. A reconciliation worker scans stale attempts using durable state, lease expiry, and heartbeat evidence.

6. Trade-offs and open questions

MySQL centralizes state consistency but requires indexed scans. At-least-once messaging simplifies recovery but requires idempotent consumers. Lease timing and provider request idempotency need environment-specific validation.
