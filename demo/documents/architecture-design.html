ENGINEERING DOCUMENT / SANITIZED CASE

异步任务编排与断点恢复架构设计方案

为长耗时、多阶段、依赖外部模型服务的工作流设计一套可靠执行架构，重点解决任务状态一致性、执行权竞争、消息重复投递和进程中断恢复。

架构决策摘要

以 MySQL 保存权威状态，以条件更新和 Fencing Token 保护唯一有效写入者；通过 Transactional Outbox 处理数据库与消息队列双写，以幂等消费接受重复投递；通过 Reconciler 对账恢复中断任务。

一、 设计目标与约束

设计目标是把长耗时 AI 工作流从请求线程中解耦，建立可恢复、可追踪、可并发控制的任务执行机制。架构优先保证状态正确和故障可恢复，不以“消息只投递一次”作为前提。

设计目标
类别目标设计原则
可靠性进程重启后可识别未完成任务并继续处理持久化状态 + 周期性对账
一致性同一任务同一时刻只有一个有效写入者数据库条件更新 + fencing token
消息接受重复投递，不因消息丢失永久卡住Transactional Outbox + 消费幂等
可观测性从 Run 追踪到 Task、Attempt 和 Artifact统一关联 ID 与事件记录
可扩展性模型供应商和执行节点可独立扩展Adapter 隔离供应商差异
非目标

本方案不保证外部模型调用本身 exactly-once，也不承诺供应商接口可撤销。系统通过幂等键、执行权围栏和结果去重，控制重复执行带来的副作用。

二、 总体架构设计

控制面负责工作流状态与调度决策；执行面通过 Worker 执行具体任务；存储面以关系数据库为权威，缓存和消息队列承担辅助能力。模块之间通过持久化状态和事件边界协作。

三、 组件职责与边界

组件职责与不可越权事项
组件职责依赖禁止承担的职责
Workflow API鉴权、创建 Run、查询进度、接收取消请求MySQL不在 HTTP 请求中等待长任务执行
Orchestrator计算节点依赖、推进节点状态、聚合 TaskMySQL不直接调用外部模型
Outbox Publisher读取待发布事件、投递 MQ、记录发布结果MySQL、MQ不改变业务 Task 的最终状态
Worker领取任务、创建 Attempt、调用 Adapter、提交结果MySQL、Redis、MQ不绕过 fencing 直接覆盖结果
Reconciler扫描超时任务、过期租约、未发布事件和不一致聚合MySQL、Redis不凭缓存状态直接判定成功
Model Adapter统一超时、限流、错误码和响应结构外部模型 API不决定工作流节点是否最终成功

四、 任务状态机与不变量

状态迁移必须由明确的条件更新完成。状态枚举建议采用 PENDING、RUNNING、SUCCEEDED、FAILED、BLOCKED、CANCELLED。终态不可被普通执行回写覆盖；重试必须创建新的 Attempt 并按策略重新进入可执行态。

五、 并发控制与写入一致性

（一） 领取执行权

Worker 领取任务时，在数据库事务中验证任务仍可执行，并递增 fencing token。只有领取成功的 Worker 才能开始处理；后续心跳只延长观察窗口，不改变 token 的单调性。

（二） 最终写入校验

执行结束时，更新必须携带当前 token 与版本号。旧 Worker 即使在租约过期后恢复，也只能得到“执行权已失效”的结果，不能覆盖新执行者的数据。

UPDATE task
SET status = 'SUCCEEDED',
    result_ref = :result_ref,
    version = version + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE task_id = :task_id
  AND status = 'RUNNING'
  AND fencing_token = :fencing_token
  AND version = :expected_version;
重要边界

必须检查受影响行数。更新 0 行意味着状态、版本或执行权不再匹配；Worker 应停止写入并记录 stale-owner 事件，不能把它当作普通成功。

六、 消息投递、Outbox 与消费幂等

业务状态与 Outbox 记录在同一事务中提交。发布器采用轮询或 CDC 读取待发布记录，投递成功后更新发布状态。若发布器在“消息已发送、状态未标记”之间崩溃，消息可能再次投递，因此消费者必须幂等。

Transactional Outbox 投递时序
100%

图 3：Outbox 解决数据库与消息系统之间的双写窗口；重复投递仍然可能发生，消费者需要去重。

  • 事件 ID 由业务侧生成并保持稳定，不能在每次重投时重新生成。
  • 消费者先建立幂等消费记录，再触发受 fencing 保护的任务领取。
  • 只有持久化成功后才 ACK；处理失败时按错误类型进入重试或死信路径。
  • Outbox 需具备积压监控、过期扫描、重试次数和人工补偿入口。

七、 失败分类与断点恢复

失败类型与处理策略
故障类别典型表现是否自动重试处理策略
网络超时 / 连接中断请求结果未知或连接异常有限重试退避重试；对不确定结果使用请求幂等键
限流 / 服务繁忙429、503 或供应商限流码有限重试遵循 Retry-After，按供应商设置并发上限
参数或权限错误明确 4xx / 权限拒绝不自动重试标记失败并提示修正配置
质量审核不通过调用成功但产物不满足质量标准策略重做进入重新生成或人工复核分支
Worker 异常退出RUNNING 无新心跳恢复后重试对账确认租约过期，递增 token 后重新领取

恢复扫描应按批次分页处理，并设置并发上限。恢复前先核实 Task、Attempt、心跳与租约；恢复后记录恢复原因、旧 token、新 token 和关联事件，避免只改变状态却无法解释原因。

九、 可观测性、安全与运维

  • 日志：所有执行日志携带 run_id、task_id、attempt_id、trace_id；敏感输入采用脱敏或摘要。
  • 指标：监控任务排队时长、执行耗时、重试率、过期租约数、Outbox 积压、恢复成功率。
  • 追踪：记录节点依赖、模型供应商、请求耗时和产物引用；不记录密钥或完整隐私内容。
  • 权限：用户只能读取其有权访问的 Run 和 Artifact；人工重试、取消、补偿必须校验操作者权限并留审计记录。
  • 运维：配置最大并发、重试上限、租约时间、心跳周期和死信保留策略，并支持按供应商隔离限流。

十、 方案权衡与待确认事项

方案权衡
决策收益成本 / 风险选择理由
MySQL 作为权威状态源事务、条件更新、审计查询较成熟高并发扫描需要索引与分片规划优先保证状态一致性
Redis 只做租约与心跳辅助降低缓存失效导致的错误裁决恢复时需要回查数据库避免缓存成为第二状态源
Outbox + 至少一次投递降低双写丢消息风险需接受重复消息并实现幂等实现成本低于端到端 exactly-once
Fencing Token阻止旧执行者覆盖新结果所有写入路径都必须带 token对付租约过期和进程暂停的关键保护

（一） 待评审问题

  1. 任务最大执行时长与租约、心跳间隔的比例如何确定？
  2. 供应商是否支持幂等请求键，未知结果的调用如何避免重复计费？
  3. 产物存储是否具备版本、校验和、过期清理及访问授权？
  4. 取消任务是否需要中断外部模型调用，还是仅阻止后续状态推进？
