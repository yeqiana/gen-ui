ENGINEERING DOCUMENT / SANITIZED CASE

AI 内容生产平台项目分析报告

围绕一个异步 AI 内容生产平台，梳理业务目标、模块边界、任务执行链路、领域模型和工程风险，展示项目分析文档应有的论证深度与证据边界。

核心结论

系统的主要工程难点不是单次模型调用，而是长流程中的任务状态收敛、外部调用不确定性、重复投递、执行权竞争和进程中断恢复。建议先把权威状态与执行权边界设计清楚，再完善质量门禁和可观测性。

一、 项目背景与分析目标

示例系统面向 AI 辅助内容生产场景，将一次创作请求拆分为策划、分镜、素材生成、质量审核和发布准备等阶段。每个阶段可能调用不同模型或外部服务，耗时与结果存在不确定性，单次请求无法保证在一个同步 HTTP 生命周期内完成。

本分析关注的重点不是模型效果本身，而是长流程任务如何可靠执行、失败如何分类、重启后如何恢复，以及过程证据如何追踪。

项目目标与主要约束
维度目标约束或说明
业务目标将创作流程拆解为可追踪、可重试、可恢复的任务外部模型调用耗时不稳定
工程目标状态可解释、执行权唯一、失败可定位消息投递可能重复，进程可能中断
数据目标保留任务、尝试、事件与产物之间的关联不能只依赖缓存或进程内状态
交互目标用户能看到阶段进度、失败原因和恢复状态页面展示不能替代后端状态校验

二、 分析范围与证据边界

本文基于一个经过重制的 AI 内容生产平台架构案例，目的是展示项目分析文档的组织方式。文中模块、实体、链路和风险均作为工程分析示例，不应理解为某个现有仓库的实时扫描结果。

分析边界

未执行目标仓库的文件遍历、依赖解析、SQL 审计、运行日志采集或压测。任何涉及现有代码是否实现、线上是否生效的判断，都必须在真实项目中重新取证。

  • 覆盖：业务流程、系统边界、模块职责、数据模型、异步任务链路、可靠性风险。
  • 不覆盖：真实模型准确率、生产吞吐量、云资源账单、实际代码缺陷数量。
  • 假设：MySQL 保存权威业务状态；Redis 用于心跳和辅助调度；消息队列采用至少一次投递语义。

三、 系统全景与模块边界

系统可拆为请求接入、工作流编排、任务调度、执行适配、持久化与可观测性六类能力。控制面负责创建运行实例和推进节点；执行面负责实际调用模型或工具；数据面保留状态与证据。

四、 核心业务链路分析

  1. 创建运行：API 校验用户权限与请求幂等键，持久化 Run 及初始节点。
  2. 节点拆分：编排器依据依赖关系生成 Task；图片或素材类任务可独立执行与重试。
  3. 任务投递：待执行任务与 Outbox 记录在同一数据库事务内写入，后台发布器再投递 MQ。
  4. 执行与回写：Worker 获取执行权，创建 Attempt，调用模型或工具，并通过带版本条件的更新写回结果。
  5. 质量门禁：技术调用成功与内容质量合格分开判断；质量不合格进入重新生成或人工复核分支。
  6. 汇总与产物：节点状态由子 Task 汇总，产物以独立 Artifact 记录，最终完成发布准备。
关键分析结论

不能用一个“节点成功/失败”字段同时表达外部调用结果、内容质量结论和用户审核结论。三者的责任主体与重试策略不同，应在数据模型中分离。

{
  "taskId": "TASK-DEMO-001",

  "attemptNo": 2,
  "fencingToken": 8,

建议让任务状态、执行尝试和产物引用保持不同生命周期。Task 代表“业务上要完成什么”，Attempt 代表“实际尝试了几次”，Artifact 代表“最终留下了什么证据或内容”。

六、 关键技术风险与问题定位

风险清单（基于示例架构推导）
风险触发条件潜在影响建议控制
数据库与 MQ 双写不一致事务提交成功但消息发布失败任务永久停留在待执行Transactional Outbox + 发布重试
租约过期后旧 Worker 继续写入任务执行时间超过租约，旧进程仍存活两个执行者覆盖结果Fencing Token + 数据库条件更新
重复消息消费者 ACK 丢失或重投重复调用模型、重复生成产物幂等键、Attempt 约束、结果去重
失败类型混淆把网络错误与质量不合格视为同一失败无效重试或错误终止分类错误码与独立重试策略
重启恢复遗漏只恢复 PENDING，忽略 RUNNING 的执行证据任务永久卡住或重复执行对账扫描、心跳过期判断、围栏接管

七、 改进建议与优先级

  1. P0 · 建立权威状态模型：明确 MySQL 为最终状态来源，所有状态更新具备合法迁移条件和版本检查。
  2. P0 · 处理双写一致性：把业务状态和 Outbox 事件写入同一事务，发布失败可重试。
  3. P0 · 防止过期执行者写入：引入递增 fencing token，所有最终写操作验证当前执行权。
  4. P1 · 分离失败语义：区分可重试的技术故障、不可自动重试的业务拒绝和质量门禁失败。
  5. P1 · 建立恢复对账：周期扫描超时 RUNNING、未发布 Outbox 和状态不一致节点。
  6. P2 · 补充可观测性：统一 Run / Task / Attempt / Trace / Artifact 关联关系。

八、 分析结论

该类系统的主要复杂度不在于简单地调用模型，而在于跨多个外部服务的长流程协调。若缺少权威状态、执行权围栏、可靠消息投递和重启恢复，局部成功并不等于整个工作流可靠。

建议的后续顺序

先验证状态机与一致性边界，再实现 Outbox、Fencing 和恢复对账，最后完善质量审核与运行可观测性。每一步都应以可重复的故障注入测试提供证据。

术语说明：Run = 流程运行实例；Task = 可调度任务；Attempt = 一次执行尝试；Fencing Token = 用于拒绝过期执行者写入的单调递增令牌。
