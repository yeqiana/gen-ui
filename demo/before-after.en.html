AOriginal AI answer

Because asynchronous tasks can fail through external API timeouts, worker restarts and repeated message delivery, the system needs persisted task states and consistent final writes. Putting events in a queue is not sufficient when a database transaction succeeds but publishing fails. A stale worker might overwrite newer work after a restart, so ownership fencing is required. Progress should be stored durably so recovery can reconcile unfinished tasks. Finally, fault injection and duplicate-consumption tests are necessary before the design can be accepted.
