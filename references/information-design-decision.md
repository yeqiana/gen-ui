# 信息设计决策（按需加载）

> 仅在任务复杂、信息类型混合或表达形式难以判断时读取。它是内部决策参考，不是固定输出模板，也不要求展示思考过程。

## 最小决策

1. **看读者任务**：读者要理解、比较、执行、判断关系，还是查阅细节？
2. **看信息形状**：单一观点、多方案同维度、顺序步骤、真实关系、层级知识，还是长篇资料？
3. **选最小表达**：优先选择能完整传达信息的最简单形式；不要为了使用图表而制造复杂度。
4. **检查理解成本**：结论是否醒目？依据、限制与推测是否分清？读者能否找到下一步？

## 形式选择

| 信息形状 | 优先形式 | 何时升级 |
| --- | --- | --- |
| 单一问题、概念或结论 | 简短段落 / 列表 | 只有存在多维关系时才增加结构 |
| 多个方案按相同维度比较 | 对比表 + 简短结论 | 维度少、差异简单时直接写段落 |
| 有先后依赖的操作 | 编号步骤；验收项用清单 | 存在分支、循环或角色交接时才用流程图 |
| 组件归属或真实依赖 | 分层容器；有证据的关系图 | 时序、数据关系、角色泳道等语义需要明确时，按需读取语义图模型 |
| 概念层级 | 标题、列表或树形结构 | 分支复杂且图能降低理解成本时才用思维导图 |
| 长篇独立交付物 | Markdown | 用户明确要求 HTML，或确有离线导航需求时再读取 HTML 合约 |

## 精简与完整

- 删除客套话、重复结论和无意义铺垫；不删除事实、证据、限制、风险或必要步骤。
- 代码、命令、路径、数字、版本、错误信息和专业术语保持准确，不为缩短而改写。
- 先给必要信息；用户要求深入，或简短表达会造成歧义、安全风险、步骤遗漏时，补充完整解释。
- 区分已观察事实、用户提供信息、推论、建议、示例和未验证事项。

## 正文语义图标
- 🎯 有依据的关键洞察；💡 有价值的新思路；❌ 可证实的错误；⚠️ 具体风险/未核实点。
- 只标记突出内容，放句首/句末；普通叙述不装饰，每段最多一个；无证据不得用 ❌。
- 避开标题、代码、标识符、原样引用和表格数据，不改原意/结构。Markdown 用 Emoji；HTML 用带 `role="img"`/`aria-label` 的 `<span class="content-marker">`；UI 图标仍用本地 SVG。

## 防止过度设计

- 用户指定的格式优先；未指定时默认 Markdown。
- 没有真实关系或可靠依据，不画连线；关系不清时用分组/容器并说明边界。
- 不为简单问题生成 HTML、仪表盘或图表；不强制每篇内容包含固定章节。
- 只有当前表达方式确实妨碍理解时才升级；不确定时优先保持简单，必要时只问一个关键问题。
