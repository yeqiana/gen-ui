# 信息设计决策（按需加载）

> 仅在任务复杂、信息混合或表达形式难判断时读取。不是固定输出模板，也不要求展示思考过程。

## 最小判断

1. **读者任务**：理解、比较、执行、判断关系，还是查阅？
2. **信息形状**：单一观点、多方案、顺序步骤、依赖关系、层级知识、长资料？
3. **选择形式**：用能完整传达事实的最小结构，不为了图表增加复杂度。
4. **阅读成本**：结论、依据、限制与下一步是否清楚？

## 形式选择

| 信息 | 首选 | 何时升级 |
| --- | --- | --- |
| 单一问题或结论 | 简短段落 | 关系复杂才分层 |
| 多方案同维比较 | 对比表 + 结论 | 维度少时直接叙述 |
| 有先后顺序的任务 | 步骤 / 验收清单 | 分支、循环、角色交接才用流程图 |
| 组件归属、真实依赖 | 分层容器 / 证据关系图 | 时序、ER、泳道需要区分语义时再读图模型 |
| 概念层级 | 标题、列表、树 | 分支复杂且图更易懂时用思维导图 |
| 长篇交付 | Markdown | 明确要求 HTML 或离线导航才用 HTML 合约 |

## 精简但不丢信息

- 删客套与重复，保留事实、证据、限制、风险和必要步骤。
- 代码、命令、路径、数值、版本、错误和术语必须准确。
- 先给必需信息；用户要求深入、简述有歧义、遗漏或安全风险时展开。
- 区分原文事实、推论、建议、演示与未验证事项。

| 证据状态 | 适当表述 | 禁止混淆 |
| --- | --- | --- |
| 来源明确 | 「当前」「已明确」 | 推测成实现细节 |
| 由事实推导 | 「据此推断」「如果…则…」 | 说成强制规则 |
| 提议设计 / 门禁 | 「建议」「需定义」 | 说成已上线或已验收 |
| 缺少日志或条件 | 「待验证」「尚不能确认」 | 断言通过、失败或阶段状态 |

压缩多轮对话时保留决定、禁止事项、数字阈值、责任和未决项；不能把「可以考虑」改写为「已采用」。

## 语义标记

- 🎯 有依据的关键洞察；💡 新思路；❌ 已证实错误；⚠️ 风险或未核实事项。
- 无证据不得用 ❌；普通叙述不装饰。突出重点才标记，通常每段不超过一个。
- 避开标题、代码、标识符、原样引用和表格数据；Markdown 用 Emoji，HTML 采用带 `role="img"`、`aria-label` 的 `content-marker`，UI 控件使用本地 SVG。

## 何时不升级

- 用户指定格式优先，未指定时默认 Markdown；不把简单问题转成 HTML、仪表盘或图表。
- 没有关系证据不画连线；不明确时用分组容器，标明边界。
- 不重复摘要；普通答复不加摘要，除非用户或其他 Skill 要求，或长文确有需要。
- 妨碍理解时才增强；必要时询问一个关键问题。
