# 阅读分层与多轮评审续接（按需）

> 仅在内容确实冗长、存在不同层次的阅读需求，或同一方案进入第二轮及以后评审时使用。不是固定报告模板；普通回答不加载。表达形式仍由 [信息设计决策](information-design-decision.md) 选择。

## 一、信息密度：按读者任务而非字数控制

| 场景 | 默认呈现 | 需要时再展开 |
| --- | --- | --- |
| 简单解释或明确问题 | 直接结论 + 必要原因 | 无须摘要、目录或装饰卡片 |
| 方案比较、风险判断 | 推荐条件 + 决定性证据/差异 + 限制 | 完整维度、反例、实施细节 |
| 长篇技术文档 | 入口说明、章节路径、关键结论 | 依据、日志、字段、代码与附录 |
| 多轮设计评审 | 本轮变化 + 当前判断 + 未决阻塞 | 已确认决策的完整依据与历史 |

- 信息按 **结论/当前决定 → 关键依据和风险 → 可执行细节** 排序，不要求每篇都出现这三个标题。
- 只压缩重复和铺垫；数字、文件路径、命令、验收阈值、禁止事项、责任、相反证据及不确定性不能因“简洁”而丢失。
- 对需要保留但非立即阅读的技术细节，Markdown 用正常小节与指向原始证据的引用；HTML 只有在明确要求时才采用已支持、可键盘操作的 `details` 等渐进展示。**折叠不是删除**，不能隐藏当前阻塞项、重要风险或最终结论。
- 用户明确要求完整报告时直接提供完整信息；不为了追求“短”强制压成固定句数，也不擅自切换输出媒介。

## 二、多轮评审：以变化续接，不重复整篇

从当前对话、用户提供的上轮文档或可核查的历史材料提取**已知**目标、硬约束、决定及证据。无法确认的历史状态写“未确认”，不能编造上一轮结论。

按需保留一份最小「决策台账」，无需数据库、自动持久化或外部服务：

| 字段 | 必须区分 |
| --- | --- |
| 议题 / 需求 ID | 对应用户目标、约束或缺陷；跨轮次沿用 ID |
| 当前结论 | 建议、已确认、待验证、被否决、已替代；不能将建议写成决定 |
| 依据 | 文件、测试、差异或用户明确确认；没有证据写“待核实” |
| 未决与处理方式 | 阻塞 / 非阻塞；待修复、待验收或由用户知情接受 |

**每轮优先说明变化**：新增或改变的事实、哪个问题解决了、哪些限制仍然有效、尚缺什么证据、下一步由谁做。未变化的已确认决定不反复铺陈；当用户请求完整记录或发生冲突时才展开历史。

## 三、评审是否收口：不等于“已经讨论很多轮”

收口前依次核对：

1. 用户要求的功能、禁止事项和验收条件是否逐项有去向；遗漏项仍记录为未决。
2. 代码或文档已修改 ≠ 已验证。未运行的测试写“未测试”，失败或未取到证据不写“通过”。
3. 未解决的问题分别记录影响、严重性、证据与处理选择。**非致命缺陷只有在影响透明、用户有权且明确接受时才标为“接受风险”**；默认为未决。
4. 按证据给出 **可收口 / 有条件收口 / 暂不收口** 的建议，并标明需要谁确认；不要自行替用户接受风险或变更需求。
5. 关键事实相互矛盾时先展示差异与待核实来源，不因追求简短而选择有利说法。

### 极简示例（虚构评审）

- **第 1 轮：** R1「旧 Worker 迟到写回」待修复；建议 fencing token，尚无测试证据。
- **第 2 轮：** R1 已有代码修改，但故障注入未运行 → **待验证**，不是“已完成验收”。
- **第 3 轮：** R1 的指定场景验证通过且有记录 → **已验证**；R2「日志字段缺失」仍未决。若用户明确接受 R2 的影响，可注明接受范围与剩余风险；否则维持未决。
- **输出只需本轮增量、当前判断和未决项**，完整历史按需提供。

本参考只约束信息表达，不替代代码评审、测试执行、缺陷优先级治理或用户授权。
